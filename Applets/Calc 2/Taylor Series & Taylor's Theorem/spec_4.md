## Pedagogical goal

Illustrate Taylor polynomials and Taylor's Remainder Theorem for Calc 2 students: how a polynomial approximates a function near a center point x₀, how the approximation improves as degree n increases, and how to compute/interpret the Lagrange error bound (using a bound M on the (n+1)th derivative over an interval [a,b]). Should let a student build intuition by dragging/typing rather than just reading a static picture.

## Design decisions log

- Function input: seven presets — eˣ, sin x, cos x, ln(1+x), 1/(1−x), arctan x, (1+x)^k (with an editable k) — plus a free-text custom expression box. Custom expressions use a hand-written recursive-descent parser (see Technical build notes), not mathjs. **Defaults to eˣ on load** (was arctan x during initial build).
- Center x₀: defaults to 0. Editable via a small badge in the graph's bottom-left corner (not inside the polynomial box — tried that first, moved it out) and via a draggable dot on the curve itself, two-way synced (drag updates the box, typing snaps the dot).
- x₀ badge styling: border in the accent color, fill matches the graph's background (not white) so it reads as part of the graph rather than a sticker on top.
- Degree n: the primary/hero control on the page — sits in its own bordered band below the graph, visually dominant. Max degree raised over several rounds: 10 → 25 → 50 (higher n is mostly useful for showing divergence outside the radius of convergence, since coefficients shrink fast inside it). Slider drag is decoupled from the committed value — a continuous internal value drives smooth handle motion while the displayed/used n only commits at whole numbers, so it doesn't feel like it's snapping between ticks. **Defaults to n=1 on load** (was n=5 during initial build — a wholly linear starting approximation reads more clearly as "the first step" than jumping straight to a degree-5 fit).
- Polynomial display: always visible (not toggleable — tried a toggle first, removed it). Highest-order surviving (non-zero) term is always highlighted as the "newest" term. Shows **exact fractions with factorial notation** (e.g. `1/5!`) when x₀ = 0 for the six presets where that's mathematically clean (eˣ, sin x, cos x, ln(1+x), 1/(1−x), arctan x); falls back to decimals for any other center, and always decimals for the binomial preset and custom functions (their coefficients aren't clean rationals in general). Truncates to the first 10 non-zero terms + "⋯" + the final term once there would be more than 11 terms shown (relevant once n got large).
- Error investigation is behind an "E" toggle (small square button next to zoom/autofit, tooltip "Investigate Errors"). Off by default so n and the polynomial own the page on first load. Toggling on reveals a side rail and resizes the graph — see Interaction details for the resize behavior constraint.
- Selected error point x: draggable on the graph (all three markers — the point on f, the point on P, and the selected-x indicator — are each independently draggable) and typeable in a box styled to match the a/b interval boxes (signals it's editable the same way). Domain-invalid x shows a warning under the box. **The selected-x indicator (the white-fill, red-stroke open circle) sits on the x-axis at the selected x-value, not at the midpoint between the f(x) and P(x) points** (changed from the midpoint placement used during initial build) — at small errors the two points sit very close together, and a circle drawn at their midpoint visually swallowed the short dashed error segment and both point-dots; anchoring it to the axis instead keeps it from ever overlapping the thing it's meant to help you read.
- Shaded error region on the graph: **spans [a, b]**, not [x₀, x] (changed from an earlier version that used [x₀, x]).
- Rail contents, top to bottom: x readout, |Error|, Rⁿ bound, then the M controls below a divider. Each of the three readouts has a one-line caption explaining what it shows. Rail is a fixed 220px (not a proportional column) specifically to leave the graph as much room as possible. Below `760px` of window height, a compact mode kicks in (see Technical build notes) that hides the captions/helper text and tightens padding/font-size so the whole rail still fits without an internal scrollbar down to ~580px of window height — the 220px width itself is unaffected.
- Rⁿ bound hides (replaced with an explanatory warning) when the selected x falls outside [a, b], since Taylor's Theorem's bound isn't valid there.
- M (the derivative bound): both a slider and an editable number box, kept in sync. "Jump to min / reset" button snaps to the smallest valid M. "Shrink to smallest possible [a,b]" button collapses the interval to exactly [x₀, x]. [a,b] auto-tracks to [x₀, x] until the student manually edits a or b, at which point auto-tracking stops. Negative M is disallowed with an explicit warning ("M can't be negative — it's a bound on an absolute value").
- M-slider range adapts as you type: upper bound = `ceil(M + 6·minValidM / √(1 + gap/minValidM))` where gap = M − minValidM — bigger gap gives proportionally smaller extra headroom, so the slider doesn't become useless after typing one huge value.
- Convergence band drawn directly on the graph (not a separate strip) with radius R computed per-preset as a function of x₀ (nearest singularity in the complex plane, e.g. R = √(x₀²+1) for arctan). Label text: "R = X.XX" and "Converges for all x inside the gray band", both left-aligned and stacked (moved from the right side, and stacked specifically to avoid overlapping each other regardless of where the band sits), pinned flush to the graph's actual top-left corner (see the `preserveAspectRatio` fix under Technical build notes — before that fix this text rendered visually well below the corner on any window whose aspect ratio didn't match the SVG's fixed viewBox). "Converges for all real x" shown instead when the function has no finite radius (eˣ, sin, cos, integer-k binomial).
- x-axis shows: (1) plain numeric tick labels at x₀, a, and b (values only, no "x₀=" style prefixes), in each marker's own accent color, and (2) **adaptive automatic tick marks** across the rest of the visible range — thin, muted-gray ticks/labels that re-pick a "nice" step (1/2/5 × 10ⁿ, targeting ~7 visible ticks) from the current view's x-span on every zoom/pan, so tick density stays sane at any zoom level. Any automatic tick that would land within `0.2 × step` of x₀/a/b is suppressed so it doesn't double up with that marker's own label.
- Default view/zoom: `xMin: -3, xMax: 3, yMin: -1, yMax: 5` (both on initial load and on pressing Reset ⟲) — widened from an earlier `-2.5/2.5/-0.53/2.67` so eˣ's curve visibly clips through the top edge of the graph rather than staying fully contained, matching a reference framing Kyle supplied. In both the old and new ranges, `yMin` is always `-span/6` and `yMax` is `5·span/6`, i.e. the origin sits a fixed 1/6 of the way up from the bottom of the graph regardless of overall zoom level — chosen so functions that only grow upward (like eˣ) get most of their vertical headroom above the x-axis instead of it being split evenly.
- Graph navigation: zoom (+/−), autofit (⤢), reset (⟲), scroll-wheel zoom, and click-drag panning on the background. Autofit and the settle-recenter that happens after dragging/typing x₀ **only ever adjust the x-range** — they never touch the y-scale, so a student's manual y-zoom is never undone by moving x₀. Reset (⟲) is a full return to the default view described above, and fires automatically whenever the function/preset changes. Note that the zoom (+/−) buttons scale around the *current view's center*, not around the origin — at high zoom levels this can carry the x-axis (and therefore x₀/a/b/the automatic ticks, all of which are positioned relative to the x-axis) below the visible viewBox entirely. This is a pre-existing characteristic of the zoom control, not a bug introduced by the tick-mark work; Reset always restores a view where the axis is visible.
- Navigation has an "auto mode" / "manual mode" split: normally (auto mode), settling on a new x₀ reframes the x-range to keep it in view. The moment the student manually pans or zooms, the app switches to manual mode and stops auto-reframing (so they can go look at something far away without the view fighting them) until they press Reset or Autofit, which snaps back to auto mode.
- Total on-screen footprint must stay constant when the E panel opens/closes — the graph should only narrow in place, not shrink the whole app. This required decoupling the graph's rendered height from its width (see Technical build notes).

## Interaction & animation details

- Toggling E animates the graph/rail split (CSS transition on the grid column widths, ~0.28s ease) rather than snapping.
- n-slider: internally driven by a continuous value (step 0.01) for the visual handle position; the committed/displayed n is that value rounded to the nearest integer. Track is thin with tick marks at each whole-number stop, and fills the full width of its box.
- x₀ and error-point dragging use pointer capture (pointerdown/move/up) so drags track correctly even if the cursor leaves the element. Settle-recenter (the x-range reframe) fires on pointerup for a drag, or on blur for a typed value — not live during the drag itself, to keep the view calm while dragging.
- Background panning: pointerdown anywhere on the graph background (not on a draggable dot) starts a pan; the draggable dots call stopPropagation so their own drags don't also trigger a pan. Panning is loosely leashed to roughly 20× the current view span around x₀ (and around f(x₀) vertically), so a student can explore but can't pan away indefinitely.
- Scroll-wheel zoom uses a native (non-passive) wheel listener specifically so preventDefault reliably stops the page itself from scrolling while zooming over the graph.

## Technical build notes

- Stack: TypeScript, compiled with `tsc` and bundled with `esbuild` into a single offline IIFE for the standalone HTML (zero external requests, verified) — same classic-transform-JSX-over-UMD-React-18.3.1 approach as Polar Graphing & Integration (see [applets.md](../../../.claude/rules/applets.md#build-model)), no `three` dependency. The same compiled source is also stripped down to a single-file JSX for the Claude.ai artifact — both are kept in sync and spot-checked to behave identically after every change. This session's round of layout/sizing fixes was hand-edited in parallel across `TaylorSeriesApplet.jsx` and the shipped HTML (no `node`/`npx`/esbuild toolchain available), matching the classic-transform `React.createElement(...)` call shape already used in the compiled file — prefer a real esbuild rebuild over hand-editing whenever the toolchain is actually available.
- Math engine: **Taylor-mode automatic differentiation** (power series arithmetic), not symbolic differentiation or finite differences. Represents functions as truncated power series and propagates them through +, −, ×, ÷, exp, ln, sin/cos (coupled recurrence), atan (via derivative/divide/integrate), and pow (via exp(k·ln(u))). This gives exact Taylor coefficients at any center x0, to any order, for both presets and custom expressions. Validated against known closed-form series before being trusted for the UI.
- Custom function parsing: hand-written recursive-descent parser (not mathjs) — needed anyway since expressions must evaluate against the power-series engine, not just plain floats.
- M's minimum valid value is found by sampling 120 points across [a,b] and taking the max of |f⁽ⁿ⁺¹⁾|, not a closed-form maximum — fine for the smooth functions in scope, but worth knowing if a wild custom function with a sharp spike is ever tested.
- **Sizing (corrected — an earlier draft of this spec described a fixed-1500px-width, CSS-`zoom`-scaled design that does not match the shipped code and never did after migration):** the app's outer card follows the same convention as every other migrated applet — `max-width: 1200px`, centered, no CSS `zoom` scaling anywhere. The card itself (not just an inner content wrapper) must carry that `max-width`/`margin: 0 auto` pair, or the gradient banner (which is the card's own top edge) stretches full-bleed across the page while the content beneath it looks correctly inset — this exact bug shipped once on this branch and was caught from a screenshot. See [applets.md](../../../.claude/rules/applets.md#build-model) for the general version of this gotcha.
- The graph's rendered height is fixed to a `min-height` floor (currently `160px`, via `.ts-graph-box`), not aspect-locked to its width — this keeps the app's total footprint constant when the E panel toggles (letting the graph's height follow its width caused the whole app to rescale whenever the panel opened), *and* stops the graph box from collapsing toward zero height on short (laptop) viewports. That collapse was a real bug on this branch: the x₀ badge is absolutely positioned *inside* the graph box, anchored to its bottom edge, so a near-zero-height box dragged the badge up into the polynomial display and degree-n slider below it, reading as everything "scrunched together." The fix pairs the floor with compact-mode padding/font tightening on the fn-input row, polynomial box, and degree-n band (all under the same `max-height: 760px` media query used for the rail) so there's still room for that floor at realistic laptop window heights.
- The error-investigation rail (`.ts-rail`) needs `min-height: 0` to be able to shrink at all — CSS Grid/Flexbox items default to `min-height: auto`, which refuses to shrink below the item's own content height, so instead of resizing the rail was silently overflowing past `.ts-card`'s `overflow: hidden` and getting clipped. Paired with `overflow-y: auto; overflow-x: hidden` (the `-x` needed explicitly, since setting only `overflow-y` makes browsers auto-compute the other axis too, which produced a spurious 1px-triggered horizontal scrollbar) as a safety net, plus the `max-height: 760px` compact-mode media query (hides `.ts-caption`/`.ts-helper-text`, tightens paddings/gaps/font-sizes) so that safety net's scrollbar essentially never has to engage in practice — verified fitting with zero deficit down to a 580px-tall window.
- The graph `<svg>` needs `preserveAspectRatio="none"` on its `viewBox="0 0 900 420"`. Without it, the default `xMidYMid meet` behavior letterboxes the SVG to preserve that 900:420 aspect ratio whenever the actual rendered graph box has a different aspect ratio (which it does — the box's height is flexible, not locked to 900:420) — this both visually pushes fixed-position overlay text (e.g. the top-left "Converges for all real x" / convergence-band labels) down away from the box's true top-left corner, and would desync pointer coordinates from data coordinates in the letterboxed margin if that margin were ever interacted with. The app's own pan/zoom code already computes `scaleX`/`scaleY` independently from `getBoundingClientRect()`, i.e. it already assumes the SVG fills its container non-uniformly — `preserveAspectRatio="none"` just makes the actual rendering match that existing assumption. Verified drag accuracy (x₀ dot lands exactly under the cursor) after this fix.
- A few root-cause bugs worth remembering so they don't creep back in if this code is refactored:
  - The "is this coefficient zero" check must use strict equality, not an epsilon threshold — the engine produces exact zeros for true-zero terms, and an epsilon threshold was incorrectly discarding legitimate tiny-but-nonzero high-order terms (e.g. 1/13!).
  - Pointer/pan handlers need to live at the `<svg>` level, not on a specific background rect sibling — sibling elements don't receive bubbled events from each other, only ancestors do.
  - Numeric input boxes must resync to the true committed (possibly clamped) value on blur, not reformat whatever raw text was typed — otherwise an invalid typed value (e.g. negative M) can look "stuck" even after the underlying state has already corrected itself.
- Card-tile hover animation (`tileType: 'taylorSeries'` in `js/data.js`, `tsTileSVG()`/`tsStartSpin()`/`tsStopSpin()` in `js/app.js`): sin x is drawn once as a dashed, muted "target" path; a single solid polynomial path lerps its sampled points between precomputed degree shapes (n = 1, 3, 5, 7 — sin x's real odd-term signs/coefficients) and rewrites its own `d` attribute every animation frame, rather than crossfading separately-drawn paths (two full-opacity curves overlapping mid-fade reads as a flicker, not one curve bending into the next). At rest (unhovered) only n=1 shows, so the resting tile still reads as "a line approximating a curve." Points are clamped in pixel space, not domain space, so a high-degree term shooting off near the domain edges just runs into the tile's border — a small, honest preview of divergence outside the radius of convergence, not a bug to hide.

_Folder: Applets/Calc 2/Polar Graphing & Integration/_

## Pedagogical goal

Help Calc 2 students build intuition for (a) how polar curves are traced out as theta varies, and (b) how polar area integration works geometrically — i.e., what the sweep of the radius line and the resulting shaded region actually represent, including the trickier case of negative r tracing the "opposite" direction.

## Design decisions log

- 2026-07-18: Left panel holds user-input functions in r = f(theta) form; each function gets its own selectable color, distinct from the black axes.
- 2026-07-18: Graphing area supports standard drag-to-pan, zoom in/out, and recenter-on-origin. No auto-fit feature.
- 2026-07-18: Theta is controlled by a slider plus numeric input boxes for the theta range; a play button animates the full sweep, with curves tracing out gradually rather than appearing all at once.
- 2026-07-18: A dashed radius line from the origin to the traced point rotates live with theta during animation, color-matched to its function; multiple functions can animate simultaneously if the user chooses to play them all at once.
- 2026-07-18: Separate "polar graphing mode" (toggled on after curves are set up) shows a theta line (sight-line) that can be dragged/rotated manually, shading the area inside a curve as it sweeps. Area-between-two-curves is deferred to a later discussion.
- 2026-07-18: When r is negative, the trace/shade extends as a dashed line in the opposite direction from the theta sight-line (which itself can extend beyond the curve to the edge of the graphing region to indicate the sweep direction).
- 2026-07-18: Theta units toggle between radians and degrees; default on load is radians.
- 2026-07-18: Function list capped at 6 slots max (typical use is 2-3). Each slot has an individual remove/clear button so Kyle can clear out a function he mistyped without resetting everything.
- 2026-07-18: Polar area mode has separate theta = a / theta = b input boxes (independent from the graphing-range boxes) that draw as visible lines on the graph as soon as populated. The draggable sight-line starts pinned at theta=a; dragging toward theta=b accumulates the shaded "pie slice" behind it, dragging back shrinks it, and dragging past either bound clamps there. A play button auto-animates the sweep from a to b at a set pace, with an auto-loop option, useful for lecture/recording.
- 2026-07-18: Function panel layout (left to right): function input → checkbox (appears when polar area mode is on) → conditional f/g dropdown (only appears once exactly 2 boxes are checked; picking a value on one dropdown auto-flips the other). 0 or 1 checked = single-curve area from origin. 2 checked = area-between-curves with f/g designation; checking a 2nd box grays out all other checkboxes until one of the two is unchecked. 3+ simultaneous not allowed. To be visually mocked up before building.
- 2026-07-18: Negative-r shaded regions need to be visually distinguishable from normal-r shaded regions but must stay clearly part of the same cohesive shaded area (same hue family, not a jarring color swap) — likely via opacity/hatching variation. Kyle also wants explanatory text to appear alongside this distinction so students understand what the visual difference means. Exact treatment TBD via mockup.
- 2026-07-18: While polar area mode is on, curves are static (no tracing animation) and the mode itself stays persistently toggled on (no forced on/off cycling just to edit a function). Hybrid clear behavior: touching the graphing-side slider or play button auto-clears the shaded region only (functions stay intact), AND there's a standalone "clear shading" button for manual reset without touching the slider. First-round implementation, open to tweaking after seeing it in practice.
- 2026-07-18: Two distinct lines, not shared: (1) Graphing-mode radius line — dashed, finite length equal to r(theta) at the current theta, traces the curve as it's drawn. (2) Area-mode sight line — solid, stretches to the edge of the graphing window regardless of r, used to sweep/paint the shaded region.
- 2026-07-18: Animation playback (graphing-side sweep and area-mode play/loop) gets a 3-way speed toggle: 0.5x, 1x (default), 2x. Open to removing/adjusting after testing.
- 2026-07-18: Visual style reuses the existing Cloud Pastel palette (most recent versions: Quadric Surfaces and Curve Sketching applets) rather than a fresh direction. OK to extend the palette with additional function colors and a shaded-region color beyond the base set, since this applet needs more simultaneous colors than prior ones; base UI chrome (panels, buttons, backgrounds) stays on-theme. Shaded-region color should aim for a clean neutral fit within the palette. Mockups needed to nail down the extended colors.
- 2026-07-18: Manual dragging of the theta line (graphing radius line or area-mode sight line) moves continuously with the mouse, no snapping to increments.
- 2026-07-18: Negative-r indicator (dashed backward line on graphing side, and the corresponding shading distinction in area mode) reuses the palette's existing soft-rose warning color rather than introducing a separate pure red — consistent with how warnings have been labeled in prior applets. Considered and ruled out as a conflict risk since warning text (near inputs) and the negative-r cue (on the graph itself) don't appear in the same visual location.

- 2026-07-18: Both the graphing-side theta range and the area-mode theta a/b bounds default to 0 to 2π on load (independent boxes, same starting values).
- 2026-07-18 (mockup review): "Polar Graphing" mode is a clearly labeled On/Off section (not a hidden/unlabeled switch) — a real behavior change (curves lock static) warrants an explicit, visible label rather than something easy to miss.
- 2026-07-18 (mockup review): Function color palette finalized as 6 hue-distinct colors: indigo #3B4FC2, coral #E0785A, teal #3FAFA0, amber #D9A441, plum #8B5FBF, slate green #5B8C5A. (First draft had indigo + light-blue too similar to distinguish; coral replaced it.)
- 2026-07-18 (mockup review): Shaded-region color is one consistent neutral tint (periwinkle-gray, ~#97A0D9) used for ALL shaded regions — both single-curve and area-between-two-curves cases — rather than tying the fill to either function's own color. This sidesteps the "which curve's color do we use for a 2-curve region" problem; the curve outlines (in their own colors) already show which curves bound the shaded area. Negative-r portions get the rose warning-color overlay on top of this same neutral base.
- 2026-07-18 (mockup review): Overall page layout — function panel, graphing controls, and Polar Graphing controls stack together as one left-side column (not below the graph), matching the graph area's height so the whole thing reads as one rectangular block. Mirrors the left-side-panel convention of other graphing tools students already know. Responsive fallback (stacking vertically on narrow/mobile screens) assumed reasonable without a separate discussion.
- 2026-07-18 (mockup review): Kyle noticed minor text/capitalization details in the mockup labels he wants to revisit — deferring that copy polish to the first real build rather than fine-tuning on the static mockup.

- 2026-07-18 (round-1 build review): Functions can be individually shown/hidden on the graph by clicking their color swatch, without clearing the typed equation or losing area-mode selection; hidden functions gray out and their checkbox disables.
- 2026-07-18 (round-1 build review): Function slot panel starts with 3 visible slots; a "+ Add another function" control reveals more one at a time, up to the 6 max, rather than showing all 6 empty slots up front.
- 2026-07-18 (round-1 build review): f/g dropdown options read "f(θ)" / "g(θ)" rather than bare "f"/"g" for clarity.
- 2026-07-18 (round-1 build review): f/g explanation combines two placements tested via mockup: a terse per-row term tag under each checked row (only shown when both are checked) plus one summary sentence + full formula below the whole function list. Kyle is not fully sold on the per-row tag piece but wants to see it in the live build before deciding whether to change it.
- 2026-07-18 (round-1 build review): When f(θ) is not the larger value across part of the shaded interval (or either curve goes negative there), that sub-interval is flagged using the same shading-style toggle as negative-r, with a note that the integral's sign flips relative to the stated f²−g² formula — keeping one consistent visual language for "the naive formula doesn't directly apply here" rather than introducing a separate treatment.
- 2026-07-18 (round-1 build review): The Graphing ⟷ Polar Integration mode switch moved out of the sidebar panel and into a new header bar (styled after the Quadric Surfaces applet's header), but all three sidebar panels (Functions, Graphing, Polar Integration) stay visible and accessible regardless of which mode is active — deliberately not collapsing the sidebar to only the active mode's panel, since that would reintroduce the "can't quickly tweak the other panel's inputs" problem.
- 2026-07-18 (round-1 build review): The original "curves are static while Polar Integration is on" decision only meant the tracing animation (slider/Play) is disabled in that mode — the graphing-side a/b range boxes stay editable and redraw the static curve immediately, since locking those too was an unintended overreach in the first build.
- 2026-07-18 (round-1 build review): θ=a and θ=b lines in Polar Integration mode get draggable text labels at the point where the line exits the currently-visible graph area (recomputed live against pan/zoom), rather than a fixed screen position, so the labels never end up off-screen.

- 2026-07-19 (round-2 build review): Applet build output format changes from a .jsx React artifact to a self-contained .html file (React/Babel loaded via CDN), matching the format used for Kyle's other applets (Quadric Surfaces, etc.) so it can be opened/hosted directly rather than only viewed in Claude's artifact panel. This applies going forward for this project.
- 2026-07-19 (round-2 build review): Fixed bug — a hidden (toggled-off) function couldn't be toggled back on, because the CSS graying out its row also disabled clicks on the swatch itself. Fix scopes pointer-events:none to the equation input only, not the swatch.
- 2026-07-19 (round-2 build review): Header mode toggle (Graphing / Polar Integration) gets a sliding "thumb" indicator with a CSS transition, matching the Quadric Surfaces header, instead of each button just getting a solid background when active.
- 2026-07-19 (round-2 build review): Confirmed the expression parser (mathjs) already supports inverse trig, logarithms, exponentials, sqrt, abs, and hyperbolic trig without any code change — e.g. atan(theta), log(theta+1), exp(theta) all work today. Revisit if Kyle hits an actual parsing error with one of these.
- 2026-07-19 (round-2 build review): Sight-line drag target gets a much wider invisible hit-area than its visible stroke width, plus a hover glow (drop-shadow), so it reads as clickable/draggable and is easier to grab.
- 2026-07-19 (round-2 build review): Header and body content now share the same max-width and horizontal padding so their left/right edges align.
- 2026-07-19 (round-2 build review): Clicking a function's × button now removes it from the list entirely (rather than just clearing its contents), shifting remaining functions up and freeing a slot to re-add via "+ Add another function." Function colors are assigned by position in the list, so colors will reassign after a removal elsewhere in the list.
- 2026-07-19 (round-2 build review): Kyle flagged the overall sidebar height while Polar Integration is on (feels too tall, doesn't want to scroll) and continued discomfort with where the f/g explanation text sits amid the grayed-out rows and add-function control. Three full-page layout mockups (including the graph area, so height can be judged against it) are in progress: (1) accordion — inactive panel collapses to a slim header, f/g info as compact inline badges; (2) merged Graphing+Polar Integration into one panel, f/g summary note relocated next to the shading controls instead of in the Functions panel; (3) Functions panel scrolls internally (capped height) while Graphing/Polar Integration panels stay fixed-height and fully visible. Decision pending Kyle's review of the full-page versions.

- 2026-07-19 (round-3 build review): Graphing and Polar Integration merged into one sidebar panel; the header toggle now smoothly expands/collapses the Polar Integration section within that panel (CSS grid-template-rows animation to natural content height) rather than swapping between two separate panels or hard-disabling one when the other is active. Play/slider still disable during Polar Integration (tracing stays paused) but the a/b range boxes remain editable either way, per the earlier round-2 fix.
- 2026-07-19 (round-3 build review): f/g explanation (single summary note + formula, with the anomaly heads-up) moved out of the Functions panel entirely and now sits inside the Polar Integration section next to the shading-style controls, per the "Option B" full-page layout mockup Kyle picked. The earlier per-row term tags (the "C" part of the combined A+C placement) were dropped in this move — Kyle can ask for them back if the simpler version feels like it's missing something.
- 2026-07-19 (round-3 build review): Function list is now a true dynamic list — clicking × removes that function entirely (list shifts up), rather than clearing its contents in place; colors are assigned by position in the list, so they can reassign after a removal. "+ Add another function" appends a new blank entry up to the 6 max.

- 2026-07-19: Standalone HTML applet builds must be fully self-contained — no external `<script src="...">` references to CDNs (unpkg, cdnjs, etc.). The v3 build initially loaded React/ReactDOM/Babel/mathjs from CDNs and failed to open/run for Kyle, almost certainly because those domains are blocked on whatever network he was opening it from. Fix, now the standing default for this project: inline the React and ReactDOM UMD production builds and the mathjs browser bundle directly into the HTML file, and precompile any JSX to plain JS ahead of time (rather than shipping Babel-standalone to transform it live in-browser) so there's no Babel dependency either. The resulting file has zero external network dependencies and should be tested by actually executing it (e.g. via a headless DOM simulation) rather than just a syntax check, since a syntax-only check won't catch a library failing to load.

- 2026-07-19 (round-4 build review): Starting state reduced from 3 functions to 2 (the two worked examples only, no extra empty third slot); "Clear all" and the id counter both reset to this same 2-function baseline.
- 2026-07-19 (round-4 build review): Hatch locked in as the final negative-r/anomaly shading treatment; the 4-way comparison toggle (rose/opacity/hatch/outline) removed from the UI now that testing is done.
- 2026-07-19 (round-4 build review): Added a small floating legend chip in the graph's top-left corner (mirroring the zoom controls' top-right placement), shown only when a hatched region is actually present. Text is context-dependent: single curve reads "Hatched = r(θ) < 0 here (curve traces to the opposite side of the origin)"; two curves reads "Hatched = f(θ) < g(θ) here (integral's sign flips)". The sidebar's fuller formula-based explanation stays as-is for anyone wanting the detail.

- 2026-07-19 (round-5 build review): Added adaptive tick-mark rings — concentric circles at a "nice number" r-spacing (1/2/5 × power of 10) chosen so rings land roughly 55px apart on screen regardless of zoom level, each labeled along the positive θ=0 axis. Rings recompute live as zoom changes rather than using fixed spacing.
- 2026-07-19 (round-5 build review): Replaced the single self-intersecting "ring" polygon (used for both single-curve and area-between-curves shading) with a fully segmented approach — the sweep is split at every point where the good/bad (hatch) condition changes, and each resulting piece is rendered as its own simple, non-self-intersecting polygon (plain fill or hatch as appropriate). This is correct by construction regardless of curve geometry, rather than relying on incidental nonzero-fill-rule winding behavior to look right, which was confirmed (by rendering the old vs. new method on Kyle's actual default curves and diffing the images pixel-by-pixel) to already produce a small but real discrepancy right at crossing points even with the default curve pair.

- 2026-07-19 (round-6 build review): Tick-mark rings now cap at the nearest axis edge distance (not the diagonal corner), so every ring drawn is a complete, uncut circle that stays within the visible axes rather than extending past them.
- 2026-07-19 (round-6 build review): Removed the "supported functions" note from the Functions panel.
- 2026-07-19 (round-6 build review): Function input accepts the "arc-" spelling of inverse trig (arcsin, arccos, arctan, arccsc, arcsec, arccot), case-insensitive — aliased internally to mathjs's native asin/acos/atan/etc. before compiling, so students can type the more familiar spelling directly.

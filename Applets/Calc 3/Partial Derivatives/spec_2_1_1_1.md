## Current status

All 6 modes (f_x, f_y, f_xx, f_yy, f_xy, f_yx) are built out and working. Mode selector, header, formula display, contextual-help structure, slider value label, and hint/summary wording are all settled and reviewed. **Production build complete**: `partial-derivatives-standalone.html` — a single self-contained file (CDN-loaded React/Babel/three.js, no build step) — is ready to host/share. One minor open item remains (tangent-line color-banding sanity check, low priority).

## Pedagogical goal

Give students a hands-on, visual way to connect partial derivatives to tangent-line slope on a 3D surface, and to build intuition for what second partials (pure and mixed) actually measure — concavity of a cross-section, and how one directional slope changes as you move along the *other* axis.

## Interaction & animation details

- **First derivative mode (f_x or f_y):** one slider (active variable), one fixed input box (other variable). Cross-section curve shown for the fixed variable's value. Point and tangent line update live as the slider moves. Badge shows the sign of the slope value itself.
- **Pure second derivative mode (f_xx or f_yy):** same slider/input pairing as first derivative. Cross-section curve shown, tangent line updates live, plus ± badge for increasing/decreasing slope (concavity framing). Color-banded tangent line treatment still pending mockup review (see Open threads).
- **Mixed second derivative mode (f_xy or f_yx):** see the fully worked-out mechanic in the design decisions log above — dashed fixed-path curve, solid live-updating cross-section curve (dim start + accent live per Option B), tangent line oriented along the "inner" derivative's direction, ± badge on the outer derivative's sign.
- Switching mode reassigns which of x/y is slider vs. fixed input, but keeps the student's current (x, y) position rather than resetting it.

## Technical build notes

**Rendering technique (locked in after several iterations):**
- 3D layer: WebGL/three.js scene containing the surface mesh (height-based vertex-color gradient, light periwinkle low → deeper indigo high, no flat-white washout), a light contour wireframe overlay, and a base grid plane.
- Annotation layer (axes, tangent line, point marker, all three cross-section curves): NOT flat 2D screen-space overlay, and NOT round 3D tubes/cylinders. Both were tried and rejected:
  - Flat SVG/canvas overlay (drawn on top of the WebGL canvas, projected from 3D world coords each frame): gives the right flat/bold look but has no knowledge of the 3D surface, so nothing drawn this way can be correctly hidden behind the opaque surface from arbitrary camera angles. Confirmed broken via screenshot (axes and curves showing through the surface where they should be occluded).
  - Round 3D geometry (TubeGeometry / CylinderGeometry, lit or unlit materials): gets correct depth-buffer occlusion "for free," but reads as a shaded 3D rod/hose/pipe regardless of material choice — rejected on visual grounds, not a technical bug.
  - **Final approach: camera-facing "billboard ribbons."** Real 3D geometry (a thin quad strip, or a triangle for arrowheads) whose vertices are recomputed every animation frame to stay perpendicular to the current camera view direction. This is genuine depth-tested 3D geometry (so the opaque surface occludes it correctly and automatically, from any orbit angle, with zero special-case logic) while visually reading as a flat, bold, 2D-style stroke (no shading gradient, no perceptible roundness) — matching the CalcPlot3D-style look Kyle wants. Implemented as reusable helpers: `makeRibbonMesh`/`updateRibbon` for lines and curves, `makeArrowMesh`/`updateArrow` for arrowheads.
- Point marker: a camera-facing `THREE.Sprite` (flat circle texture, depth-tested), not 3D geometry — sprites are automatically billboarded, so this was the simplest correct option.
- **Zoom-invariant width:** ribbon/arrow half-widths are scaled per-vertex by `distance-from-camera / referenceDistance` (reference = the initial camera distance at mount). This keeps the on-screen apparent thickness constant regardless of how far the student has zoomed in/out — without it, ribbons naturally get thicker on-screen when zoomed in, which is the world-space vs. screen-space tradeoff inherent to this technique.
- Axis rods stop short of their arrowhead tip (pulled back by the arrow's length along the axis direction) rather than sharing the tip's exact endpoint — otherwise the rod's constant width pokes visibly past the arrowhead's tapered tip.
- Dashed fixed-path curve: implemented as a per-vertex width multiplier (0 or 1) following an on/off point-index pattern, NOT a true `stroke-dasharray`-style effect (ribbons don't support that natively). Needs a higher point-count curve (currently 220 pts, vs. 60 for the other curves) to render short/frequent dashes cleanly — coarser point counts make the dashes look chunky.
- Custom manual orbit-drag + scroll-zoom camera controls (no external OrbitControls dependency, since three.js examples/addons aren't available in this environment — base `three` r128 only). Vertical orbit angle (phi) is clamped so the camera can't dip below roughly the horizon — it always looks down at the surface from above. This means the "occlusion via depth test" approach hasn't been tested/exercised for below-the-surface viewing angles; if under-the-surface viewing is ever opened up, worth re-confirming occlusion still behaves correctly (it should, since it's real depth-tested geometry, but untested at those angles).
- Attempted `react-plotly.js` for the 3D surface first; it failed to load/render in this environment. Switched to hand-rolled three.js rendering, which has been the approach ever since.
- Fixed-value input box uses a text-buffer pattern (raw string kept in local state while typing, reconciled/clamped on blur) rather than direct `parseFloat`-on-change, which was fighting the user mid-keystroke.
- Cross-section curves for all 6 modes are generated by one shared helper (`crossSection`) that varies one axis over the domain while holding the other fixed — the mode config (`sliderVar`, `fixedVar`, `tangentDir`, `mixed`) drives which axis plays which role, rather than each mode having bespoke curve-building code.
- Mesh visibility for the dashed path curve and dim-reference curve is toggled per-frame based on whether the current mode is a mixed mode, so switching out of f_xy/f_yx doesn't leave stale ribbon geometry rendered at its last position.
- Info-icon tooltips are implemented as a small reusable `InfoTip` component (absolute-positioned popover, opens on hover or click, no external dependency) so they don't consume layout space until opened.
- The formula display and orbit/zoom hint are absolutely-positioned overlays inside the graphing card (not separate cards), with a semi-transparent white backdrop for legibility against the rotating surface.
